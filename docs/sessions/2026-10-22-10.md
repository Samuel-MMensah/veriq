# Session 2026-10-22-10: Prompt 5, The report loop

## Summary
Patients can now report whether their card worked, in three taps, even without a connection. The report waits on the phone and sends itself when the phone is back online. The server applies rule A (hashed device id, one report per hospital per week, burst holding). The thanks screen says exactly what the report changed on the hospital page, recalculated with the rules. Tested on fresh sample data and on the live Supabase project.

## How to check it yourself
1. Run `npm run dev` and open the Akoma page from a NHIS search. Tap "Been here? Tell others if your card worked".
2. Choose "Yes, but I paid extra", type 80, tap Scan, then Send. The thanks screen says Akoma now shows "Scan top-up about GH¢ 80 (4 patients, last 60 days)". This writes to your live Supabase project unless you run with `VERIQ_DATA=local`.
3. Open the same report page again and send any answer: "already counted".
4. In Chrome DevTools → Network, set "Offline", send a report: "Saved on your phone." Turn the network back on: it sends by itself.

## Problems and risks
- Reports you send while trying the app on live Supabase change the demo data, e.g. Akoma's top-up count. Re-run the seed before a demo; Prompt 8 adds a one-click reset: medium
- Vercel and Supabase still see the caller's IP address in their own request logs. We never store it, but the Phase 2 privacy notice should say so: low
- Someone could clear site data to get a new device id and report again. Rule A's burst holding limits the damage; Phase 2 admin review handles held reports: low
