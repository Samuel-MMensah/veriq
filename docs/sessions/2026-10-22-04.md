## How to check it yourself
1. Run `npm test`. The test names in `supabase/tests/seed.test.ts` read like a checklist of the demo story.
2. To load it into Supabase:
   1. Create a free project.
   2. Run `npx supabase init`. It adds `supabase/config.toml`; keep the existing files.
   3. Run `npx supabase link --project-ref <ref>`, then `npx supabase db push`.
   4. Paste `supabase/seed.sql` into the SQL editor and run it.
   5. In Table editor → facilities, check that there are 18 rows, all with `is_sample = true`.
3. Copy `.env.example` to `.env.local` and fill in:
   - `NEXT_PUBLIC_SUPABASE_URL`: Project Settings → API → Project URL
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`: the anon (or "publishable") key
   - `SUPABASE_SERVICE_ROLE_KEY`: the service_role (or "secret") key. Server only; never commit it.

## Problems and risks
- The SQL hasn't run on real Supabase yet. The shim only imitates Supabase's `auth.uid()` and roles. Run `db push` and the seed early: medium
- The query tests use a stand-in for supabase-js, not real PostgREST, so a filter that behaves differently there wouldn't be caught: low
- `public_card_reports` is a "security definer" view, so Supabase's advisor will flag it. That's intended (it hides the device hash), but it means the view bypasses row-level security by design: low
- The screen images show figures 18 hospitals can't reach (142 hospitals on the list, 3,410 searches), so the insurer screen will show smaller sample numbers: low
- Re-running the seed clears `search_daily`, so searches logged during a demo are lost on "Reset demo data". That's fine for Phase 1: low
