# Decisions

One line per decision the spec didn't make: date, decision, reason.

- 2026-10-22: The PROGRESS.md screen table has Route and Phase columns. Reason: Prompt 0 asks for each screen's phase.

- 2026-10-22: TypeScript pinned to 6.0, not 7. Reason: typescript-eslint (used by eslint-config-next) supports only TypeScript below 6.1.
- 2026-10-22: `/saved` shows a one-line "coming in the pilot" note. Reason: the bottom bar must have a Saved tab (section 2), but screen 9 is Phase 2, so the tab shouldn't 404 and the screen shouldn't be built early.
- 2026-10-22: Phase 2 and 3 route folders, `app/api/*`, `lib/*` and `supabase/migrations` exist only as empty folders (`.gitkeep`). Reason: section 5 asks for the folders; rule files are written tests-first in Prompt 3, and later-phase screens wait for their gate.
- 2026-10-22: PWA icons are SVG for now (normal and maskable). Reason: there are no brand assets yet; PNG icons can be added during the Prompt 8 polish.
- 2026-10-22: No service worker yet, only the manifest. Reason: Prompt 1 asks for the manifest; offline behaviour comes with the report queue (Prompt 5) and screen 12 (Phase 2).
- 2026-10-22: SAMPLE DATA tag goes on the hospital-data screens (find, results, hospital detail, report, thanks, emergency, morning check, insurer network), not on first open, how we check, help or my cards. Reason: rule 1 covers "screens with data"; cards are the user's own device data.
- 2026-10-22: Playwright tests a production build on port 3100 at 390 px wide (Pixel 7 profile). Reason: rule 7 (mobile first), and a production build is closer to the deployed site.
- 2026-10-22: Staff screens (`/h/*`, `/i/*`) do not show the patient bottom bar. Reason: section 2 calls it the patient bottom bar.
- 2026-10-22: Patient screens have a white background; page grey (#F4F6F5) is for panels inside a screen. Reason: the screen images show white screens, and section 2 says to match the images' colours.
- 2026-10-22: First open (`/`) stays in the `(patient)` folder as section 5 says, and the bottom bar hides itself there. Reason: screen 7 is a full-screen welcome with no bottom bar.
- 2026-10-22: `insurers` has a `slug` column (e.g. `nhis`). Reason: the results URL carries the card as `card=`, and a short readable id is better there than a UUID.
- 2026-10-22: `hospital_responses` has a nullable `item` column. Reason: rule T works per facility, insurer and item, so a top-up confirmation or correction must say which item it is about.
- 2026-10-22: `search_daily` has a `searches` count column. Reason: section 3 lists only the key fields; a counts-only table needs a count.
- 2026-10-22: `facilities.is_sample` defaults to true. Reason: rule 1, so nothing can be added as real data by accident before Phase 2.
- 2026-10-22: Live reports are read through a `public_card_reports` view without `device_hash` or `state`; the `card_reports` table has no public read policy. Reason: section 3 lets anyone read live report counts, and rule 2 keeps device hashes private.
- 2026-10-22: A trigger stops anyone but admin changing `facility_insurers.listed_by`, and only admin writes the `facilities` row itself. Reason: hospitals may confirm their own cards (rule M) but must not put themselves on a list or mark themselves verified.
- 2026-10-22: `area_cell` is the south-west corner of a 0.02 degree cell (about 2 km), written "lat,lng" with two decimals. Reason: rule K says cells of about 2 km; Prompt 3's lib/geo.ts must use the same format.
- 2026-10-22: Sample phone numbers are deliberately invalid (`+233 000 000 0NN`). Reason: an invented hospital must never ring a real number.
- 2026-10-22: The seed tells the insurer story for NHIS: 23 refusals at 6 hospitals, Pinecrest 9, and Akoma not on the NHIA list but confirmed by the hospital. Reason: it fits the demo script and screens 2, 3 and 18 together. Where the images disagree (Akoma "9 patients agree" vs "12 members served"), the patient screen wins: 9. Confirmed by the team on 2026-10-22: the demo insurer login (Prompt 7) is NHIS.
- 2026-10-22: Database tests run the real migrations and seed in PGlite (in-memory Postgres) with a small Supabase shim, plus a minimal stand-in for the supabase-js query builder. Reason: there is no Docker or Supabase project on this machine, and it keeps `npm test` self-contained.
- 2026-10-22: Migrations and the seed are pushed with `npx supabase db push --db-url "$SUPABASE_DB_URL" [--include-seed]`, using the Session pooler URI kept in `.env.local`. Reason: the direct database host is IPv6-only and doesn't resolve on this network; this avoids `supabase login`.
- 2026-10-22: `supabase/config.toml` (from `supabase init`, default settings) is kept in the repo. Reason: `db push --include-seed` reads the seed path from it, and Prompt 8's reset will need the same seed.
- 2026-10-22: Rule B1 compares refused with accepted using only reports newer than `hospital_confirmed_at` (all of the last 30 days if there is no answer). Reason: the spec's "more refused than accepted" doesn't say which reports; a fresh hospital answer should reset both sides.
- 2026-10-22: Rule windows include their boundary: "last 30/60 days" includes exactly 30/60 days, and "within 14 days" includes exactly 14. A device may report again exactly 7 days later; a status exactly 24 h old is "may have changed" and exactly 72 h is still "may have changed" (over 72 h is stale). Reason: the spec gives the numbers but not the edges; tests pin each one.
- 2026-10-22: In rule S1, a status over 72 hours old sorts as "unknown". `working` and `from_time` count with open/accepting, and `down` with closed/full. Reason: S2 already treats stale as unknown, and a days-old "open" shouldn't outrank a hospital with no update.
- 2026-10-22: Rule A burst: if 10 or more reports for the facility (any state) arrived in the last hour, the new one is held, so the 11th and later are held. Reason: "more than 10 in an hour".
- 2026-10-22: Device hash is SHA-256 of `deviceId + ":" + secret`. Reason: the spec says id plus secret; the separator keeps the two parts distinct.
- 2026-10-22: Rule T: a `confirm_topup` counts only if it is newer than the newest patient top-up report. A `correct_topup` is overridden when 2 or more newer reports differ from it after rounding to GH¢ 5; the amount then shown is the median of those newer reports. Reason: the spec says "newer" and "disagree" without defining them.
- 2026-10-22: Rule K counts both `listed_by = nhia` and `listed_by = insurer` as "on the list". Coverage gaps sum the search log's `had_confirmed_result = false` counts per cell, named after the nearest hospital's area within 10 km. Reason: for NHIS the list is the NHIA list; the search log already records whether a B2/B3 hospital was found within 5 km.
- 2026-10-22: Shared time helpers (`lib/rules/time.ts`: windows, ages, "40 min" wording) sit beside the rule files. Reason: badge, freshness, top-up, limits and K all need the same boundaries and wording.
- 2026-10-22 (team decision): History is kept and every count names its period. Badges carry accepted/refused counts for the last 7 days, 30 days and 12 months (`lib/rules/history.ts`), and queries fetch 12 months of reports. New refusals must not disappear: B1 still compares only reports since the hospital's answer, but its text counts every refusal in the last 30 days. Wording changes from SPEC section 4: B1 "Listed, but {n} patients were refused in the last 30 days", B3 "{n} patients confirmed in the last 30 days", top-ups add "({n} patients, last 60 days)". Reason: the team asked for clear week/month/year references and for history not to be lost. SPEC.md still has the old wording and needs updating by the team.
- 2026-10-22: Held and rejected reports stay in the database for good; they are only left out of counts (rule A). Reason: the team asked that rejected data not disappear.
- 2026-10-22: Local data mode: `VERIQ_DATA=local` runs the real migrations and seed in PGlite inside the server (`lib/db/server.ts`). Playwright uses it. Reason: the live seed's times drift (Akoma's "2 days ago" expires after 14 days), so e2e needs fresh data on every run, and the app can run without keys.
- 2026-10-22: Searches are counted through a `log_search` database function that only the service role may call (migration 3). Reason: rule K needs a count per card, day and cell; an increment needs a function, and the browser must not be able to inflate counts.
- 2026-10-22: Each Find chip searches one service: Scan / X-ray → ultrasound, Specialist → obstetrician. Reason: one service per search keeps "today's status for the chosen service" (screen 2) unambiguous; more services per chip can come later. (Replaced the same day, see below.)
- 2026-10-22 (team decision): Find chips cover several services. Antenatal / maternity = antenatal, delivery and C-section; Scan / X-ray = ultrasound, X-ray and CT; Specialist = obstetrician and children's doctor. A result shows the matching service with the best status today (`bestStatus` in lib/rules/sort.ts, same ranking as S1, newest among equals) and names it, e.g. "Ultrasound scan: Available". Chip slugs go in `?service=`; a plain service id still works. Reason: the team wants the app to be outstanding but realistic.
- 2026-10-22: `REPORT_HASH_SECRET` was generated (48 random bytes) into `.env.local` only, never printed or committed; `.env.example` lists it empty. Reason: rule A needs it from Prompt 5; the team will replace it later.
- 2026-10-22: The Find form is a plain GET form with real radio buttons; JavaScript only adds GPS, the live button label and remembering the last area (localStorage). Reason: rule 7 (cheap phones, 3G) and rule 8 (last search area cached).
- 2026-10-22: Typed areas are a fixed list of Accra areas with coordinates (no geocoding service). Dansoman is the default. Reason: no external service in Phase 1, and it keeps the demo predictable.
- 2026-10-22: "No card/cash" lists every facility in the radius that offers the service, sorted by status then distance (`sortNoCard` in lib/rules/sort.ts). Reason: badges need a card; section 2 says B5 shows under "No card/cash".
- 2026-10-22: Result cards show the badge as "{card} · {rule B text}". Reason: keeps the exact rule wording while saying which card it is about.
- 2026-10-22: The patient bottom bar is hidden on sub-pages with a back arrow (hospital detail, report, how we check, emergency). Reason: the screen images show no bar on screens 3, 6 and 14.
- 2026-10-22: Added the `refused-ink`, `patient-ink` and `emergency-bg` colour tokens. Reason: the section 2 orange and light green are too faint for small text on their pale backgrounds; the spec colours stay for icons, borders and dots.
- 2026-10-22: Share and Save are left off the hospital page, and the Map button shows "Map soon". Reason: screens 8, 9 and 10 are Phase 2.
- 2026-10-22: On the hospital page, services with no update are listed in one "No update yet:" line instead of one tile each. Reason: matches the screen image while still saying so (rules 4 and F).
- 2026-10-22: `lib/view/` holds plain functions that turn query rows and rule results into what each screen shows. Reason: keeps pages free of logic, and they are unit-tested on the seed.
- 2026-10-22: `lib/db/types.ts` is written by hand. Reason: there is no Supabase project to generate it from yet; `supabase gen types` can replace it later.
